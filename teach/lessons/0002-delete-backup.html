What it is

delete-backup is a Claude Code mod that watches Bash calls and adds one slash command, /undo-delete. Before a Bash command runs rm, it copies each target that exists into a time-stamped backup folder, and only then lets the command run. /undo-delete puts the newest complete backup back at its original paths, and it never writes over a path that is already in use.

It matters for your mission because MISSION.md asks you to point to the hook events and API calls each mod uses and say why, and this mod is small enough to trace all the way through.

How it was built

The whole mod is one hooks file, register.ts, about 500 lines. The steps below follow the order the code runs in.

1. Hook Bash and read the command as tokens

The hook runs on every Bash call, but it only needs to act when a command could delete something or move the shell's folder. So it first looks for the words rm, cd or one of the folder words. If none is there, it returns next(e) and the call goes ahead untouched.

  on('tool.call', { tool: 'Bash' }, async ($, e, next) => {
    const tokens = tokenize(e.command)
    if (!tokens.some(t => t.kind === 'word' && (t.text === 'rm' || t.text === 'cd' || FOLDER_WORDS.has(t.text)))) {
      return next(e)
    }

The check runs on tokens, not on the raw text. A small tokenizer splits the command into words, operators and substitution markers. It keeps quoted text as one word. A $( or a backtick is marked wherever it appears, even inside single quotes where the shell would not run it. That is the cautious side.

Why not search the text for rm? A search would also match a quoted commit message, a path such as ./rm, or echo rm. It also could not tell where one command ends. Tokens show which word starts each command, and the hook only reads that word.

    let op: string | undefined
    if (c === '\n' || c === ';') op = ';'
    else if (c === '&' && next === '&') op = '&&'
    else if (c === '|' && next === '|') op = '||'
    else if (c === '|') op = '|'
    else if (c === '&' && next !== '>' && command[i - 1] !== '>' && command[i - 1] !== '<') op = '&'
    else if (c === '(' || c === ')') op = c
    else if ((c === '{' || c === '}') && !inWord && (next === undefined || /[\s;&|()]/.test(next))) op = c

    if (op !== undefined) {
      endWord()
      out.push({ kind: 'op', text: op })
      if (op === '&&' || op === '||') i++
      continue
    }
A failing guard is denied, not skipped. The engine skips a hook that throws, so an unguarded failure would let the command run. This hook ends with a .catch. If it fails before it calls next, the Bash call is denied. If it fails after next has run the command, the catch returns that result and does not run the command again.

2. Follow the shell's folder across calls with $.store

The hook does not read the Bash shell's folder. It follows each cd itself, and it keeps the result in $.store, the plugin's own JSON store. The key is folder: followed by the session id and the agent id, so a subagent has its own folder. A call with no saved key starts at $.session.cwd(). A saved null means the folder is unknown.

    // The folder the Bash shell is in is kept per session, so a cd in one call holds for the next.
    const key = `folder:${await $.session.id()}:${e.agentId ?? 'main'}`
    let walk: Walk
    try {
      const stored = (await $.store.get(key)) as { folder: string | null } | undefined
      const start = stored === undefined ? await $.session.cwd() : (stored.folder ?? undefined)
      walk = await follow($, tokens, start)
      const held = holdReason(walk)
      if (held !== undefined) {
        return { deny: held }
      }
      await backUp($, walk.jobs, e.command)
    } catch (error) {
      return { deny: `delete-backup held this command: ${reason(error)}. Nothing was deleted.` }
    }

    const ran = await next(e)
    if (ran.deny === undefined) {
      await $.store.set(key, { folder: walk.folder ?? null })
    }
    return ran

The function follow walks the command in order. Each cd runs in a bash process, which shows whether it worked and prints the physical folder with pwd -P. Each possible folder is kept as a state with a status: ok, fail or unknown. A failed cd leaves the folder where it was. Every other command is unknown, because the hook does not know its exit code. After && a unit runs only in ok states. After || it runs only in fail states. An unknown state splits into both. Past 16 states, the folder becomes unknown.

The saved folder is written only when the call was not denied. A denied call did not run, so the shell did not move.

The hook denies the whole Bash call when an rm would run in a folder it cannot name. The reasons are checked in jobWhy:

function jobWhy(job: Job, walk: Walk): string | undefined {
  if (walk.grouped) return 'the command has a subshell or grouping'
  if (walk.cdMinus) return 'the command has cd -'
  if (job.subst) return 'the rm has a $( or a backtick'
  if (job.targets.some(target => target.includes('$'))) return 'an rm target has a $'
  if (job.folders.length > 1) return 'the rm may run in more than one folder'
  if (job.folders[0] === undefined) return 'the working folder is unknown (run cd with an absolute path to set it)'
  return undefined
}
  • Subshells and groups. The walk handles a ( ) subshell only roughly, and treats a { } group as a plain separator. So a command with either one is refused when it has an rm. A $( counts too, because its parenthesis is an operator.
  • cd -. The previous folder is not tracked.
  • Substitution and $. A $( or backtick in the rm, or a $ in its target, would need the shell to expand it.
  • More than one folder. After make && cd build, the rm may run in either folder.
  • Unknown folder. A cd with a $, a backtick or a ~user path makes the folder unknown. So does a relative cd when the folder is already unknown. A pipe or & in the command makes any cd unknown, because that cd may run in a subshell.

Why refuse rather than guess? A wrong folder means the backup copies the wrong files, or none, while the rm deletes the real ones. The reason text says nothing was deleted. That holds because the call is stopped before it runs.

A gap the README does not mention. The walk reads only the first word of each command, after an optional sudo. Words that open a compound command hide the command after them. They are do, then, else, elif, while, until, time and !. In if [ -d build ]; then cd build && rm -rf dist; fi the cd is not seen, so the rm is checked in the wrong folder, and the files it really deletes are not copied. In for f in a; do rm "$f"; done the rm is neither backed up nor denied. I found this by reading the code. I did not run it.

3. Find the targets that exist

For each rm, the hook runs a bash process in the folder the rm would run in. The process runs the RESOLVE script and prints only the targets that exist. The script expands ~ and globs. IFS is cleared, so a name with a space stays whole. Relative paths are made absolute from $PWD. A path is kept when -e or -L is true, so a broken symlink still counts. The output is NUL-separated, which keeps odd file names intact.

const RESOLVE = [
  'shopt -s nullglob',
  'for t in "$@"; do',
  '  case "$t" in "~") t=$HOME ;; "~/"*) t="$HOME/${t#"~/"}" ;; esac',
  '  IFS=',
  '  for p in $t; do',
  '    case "$p" in /*) ;; *) p="$PWD/$p" ;; esac',
  '    case "$p" in */.|*/..) continue ;; esac',
  "    if [ -e \"$p\" ] || [ -L \"$p\" ]; then printf '%s\\0' \"$p\"; fi",
  '  done',
  'done',
].join('\n')

The targets are passed as arguments, after the script text. The script reads them as "$@", so they are only data. They are never pasted into the script. A quote or a ; in a file name therefore cannot change what the script does.

async function existing($: EngineInterface, job: Job): Promise<string[]> {
  const ran = await $.process.run(['bash', '-c', RESOLVE, 'delete-backup', ...job.targets], { cwd: job.folders[0] })
  if (ran.exitCode !== 0) {
    throw new Error(`could not read the rm targets: ${ran.stderr.trim()}`)
  }
  // A cut list would leave some targets without a backup.
  if (ran.isStdoutTruncated) {
    throw new Error('the rm targets match too many paths to list')
  }
  return ran.stdout
    .split('\0')
    .filter(path => path !== '')
    .map(trimSlash)
}
Three edge cases from the code. (1) The skip for . and .. only matches paths that end in /. or /... A target of ./ or ../ is not skipped. After the trailing slash is trimmed, ./ copies the folder the rm runs in, and ../ copies its parent. (2) RESOLVE and CD set no timeoutMs, so the 30-second default applies to them. (3) Output is capped at 4 MiB. If the list of targets is cut (isStdoutTruncated), the hook refuses the delete rather than back up only part of it. (4) Shell keywords such as if, then, do and else are skipped, so then rm -rf build still counts as an rm. A cd after a keyword may sit in a branch that does not run, so it makes the folder unknown, and a later relative rm is refused. Points (3) and (4) were fixed after this page was first written. They were checked with Node against real bash, but the mod has not run in a live session.

4. Copy each target before the rm runs

backUp runs after the walk and before next(e), so the copies exist before anything is deleted. First it drops duplicates. It also drops any target that sits inside another target, so build and build/dist give one copy of build. It makes one folder named by the time, with colons and dots changed to dashes. Then it copies each target with cp -Rp, which copies folders recursively and keeps modes and times. Each item gets a number in front of its name, so two files with the same name do not clash. Each copy is its own process with a ten-minute limit.

  const now = await $.clock.now()
  const folder = `${await backupRoot($)}/${stamp(now)}`
  const made = await attempt($, ['mkdir', '-p', folder])
  if (made !== undefined) {
    throw new Error(`could not create ${folder}: ${made}`)
  }

  const items: Item[] = []
  for (const [index, original] of found.entries()) {
    const backup = `${index + 1}-${nameOf(original)}`
    const copied = await attempt($, ['cp', '-Rp', original, `${folder}/${backup}`])
    if (copied !== undefined) {
      throw new Error(`could not copy ${original}: ${copied}`)
    }
    items.push({ original, backup })
  }

  // The manifest comes last, so a folder without one is an incomplete backup that restore skips.
  const manifest: Manifest = { time: new Date(now).toISOString(), command, items }
  await $.fs.write(`${folder}/manifest.json`, `${JSON.stringify(manifest, null, 2)}\n`)

The manifest comes last. It holds the time, the command and the list of original paths with their backup names. A folder with no manifest.json is an incomplete backup, and restore skips it. A failed copy throws. The hook then denies the Bash call, so the rm does not run.

The copy is wider than the README says. The README says a backup holds what the rm would delete. The code copies every target that exists, whatever flags rm gets. A plain rm of a folder would refuse, and the hook still copies that folder first.

5. Restore the newest backup with /undo-delete

The command is handled by a command.run hook. It calls restore, which finds the newest folder under the backup root that has a manifest. The folder names are ISO times with safe characters, so sorting the names sorts them by age.

async function newestBackup($: EngineInterface, root: string): Promise<string | undefined> {
  const folders = (await entriesOf($, root))
    .filter(entry => entry.kind === 'dir')
    .map(entry => entry.name)
    .sort()
    .reverse()

  for (const name of folders) {
    if (await $.fs.exists(`${root}/${name}/manifest.json`)) {
      return name
    }
  }
  return undefined
}

For each item, putBack checks first. If a file with that name is already in the parent folder, it refuses that item and touches nothing. Otherwise it makes the parent folder and copies the backup back with cp -Rp.

async function putBack($: EngineInterface, folder: string, item: Item): Promise<string | undefined> {
  if ((await namesIn($, dirOf(item.original))).includes(nameOf(item.original))) {
    return 'a file is already at that path'
  }

  const made = await attempt($, ['mkdir', '-p', dirOf(item.original)])
  if (made !== undefined) {
    return made
  }
  return attempt($, ['cp', '-Rp', `${folder}/${item.backup}`, item.original])
}

Each item is tried on its own. If every item comes back, the mod removes the backup folder with rm -r. It runs that through the process API, not as a Bash call, so the tool.call hook does not see it. If any item fails, the backup stays and the reply names its folder.

A partial restore repeats. If one item fails, the next /undo-delete restores the same newest backup. The items that already came back now show as existing, so they are reported as failed again. The README describes the same result.

How to use it

claude plugin install delete-backup@waraxe-claude-mods

The source does not give that path.

  • Work as usual. Run Bash commands as you normally would. Before an rm runs, its existing targets are copied. A Bash call with an rm the hook cannot place is denied, and the reason is shown.
  • Undo the newest deletion. Run /undo-delete. It puts the newest complete backup back at its original paths and lists what it restored.
  • Find the backups. They are in ~/.claude/delete-backup, with one time-stamped folder for each Bash call that had something to copy. Each folder holds the copies and a manifest.json.
  • Know the cost. Each covered rm copies what it would delete first. A large rm -rf, such as one on node_modules, takes time and needs about as much disk space again. Nothing is pruned automatically, so delete old backup folders yourself.

Limits, from the README:

  • Only rm, optionally after sudo, is covered. find -delete, xargs rm and git clean are not. Neither are /bin/rm, command rm, Write or Edit.
  • Shell variables and $(...) are not expanded. An rm with a $ is denied rather than backed up.
  • Only the newest backup is restored each time. Older backups stay until you delete them.
  • When the folder cannot be known, as after make && cd build, rm is denied until a Bash call runs cd with an absolute path.
Where the README and the code differ.
  • The README says a cd with an absolute path sets the folder. The code also accepts ~, ~/..., and a bare cd, which goes home.
  • The README says rm may follow sudo. The code strips one sudo only. sudo -E rm and a leading VAR=value rm are not seen. The README does not say so.
  • The README's list of denied cases leaves out an rm that may run in more than one folder. The code denies that case.
  • The README says a backup holds what rm would delete. The code copies every existing target (step 4).
  • Compound-command words such as then and do hide the command after them. The README is silent on this (step 2).
  • ./ and ../ are not skipped (step 3).

Check yourself

Why does the hook read the command as tokens instead of searching the text for rm?

A text search would match rm inside quoted text or a path, and it cannot tell where one command ends. Tokens keep quoted text as one word and split at the operators, so the hook can see which word starts each command.

Why is manifest.json written last?

Restore looks only at folders that have a manifest.json. Writing it last means a folder with a manifest has every copy in it. If a copy fails part way, the folder has no manifest, and restore skips it.

You run make && cd build in one Bash call, then rm -rf dist in the next. What happens?

The hook denies the rm, with the reason that the working folder is unknown. The cd may not have run, so the hook cannot name the folder. A Bash call that runs cd with an absolute path sets the folder again.
