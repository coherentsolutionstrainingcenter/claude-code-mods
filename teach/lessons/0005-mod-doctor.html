What it is

Mod doctor adds a pane that you open with /mod-doctor. The pane reads your installed plugins from claude plugin list, then runs claude plugin validate on each enabled one that has a folder. It shows each verdict with the hook events and calls the plugin declares, and it raises three plain flags.

Your MISSION.md asks you to name the hook events and calls each mod uses and to check a change with claude plugin validate, and this pane gives you both for every installed mod at once.

How it was built

The mod has one hooks module, hooks/register.tsx. hooks/hooks.json points to it, and plugin.json does not list hooks itself. The build has four parts.

1. List the plugins

The mod runs $.process.run(['claude', 'plugin', 'list'], { timeoutMs: 60000 }) and parses the text it prints. A line such as ❯ name@marketplace starts a row. The Version, Read from and Status lines fill in that row. Only a Read from line gives a folder. The Status line counts as enabled when it has the whole word enabled or loaded, so disabled does not match. If the list exits with a non-zero code, the audit stops and the pane shows up to 300 characters of the error output.

/** Reads the rows of `claude plugin list`. Only a "Read from:" line gives a folder. */
function parseList(text: string): Installed[] {
  const rows: Installed[] = []
  let row: Installed | null = null

  for (const line of text.split('\n')) {
    const head = line.match(/^\s*❯ (\S+)\s*$/)
    if (head) {
      row = { id: head[1], version: '', enabled: false, folder: null }
      rows.push(row)
      continue
    }

    const field = line.match(/^\s+(Version|Read from|Status):\s*(.*?)\s*$/)
    if (row === null || field === null) {
      continue
    }
    if (field[1] === 'Version') {
      row.version = field[2]
    } else if (field[1] === 'Read from') {
      row.folder = field[2]
    } else {
      row.enabled = /\b(enabled|loaded)\b/.test(field[2])
    }
  }

  return rows
}
Why text, not --json.

The source does not say why it avoids the JSON form. It only says that a Read from line gives a folder. On this machine, the JSON installPath of an installed mod sat under ~/.claude/plugins/cache/, while the text form's Read from line named the marketplace folder. That fits a cache copy being the wrong place to read from. I did not check a plugin installed from GitHub, so its paths may differ.

2. Validate each enabled plugin

For each enabled plugin with a folder, the mod runs claude plugin validate with the folder as one argument, so no shell reads the path. The run's stdout and stderr are joined, and the parsing reads that text. If the run throws, the check gets the verdict unknown, and the error message becomes its problem.

/** Runs the validator on one plugin folder. A run that cannot finish gives no verdict. */
async function validateOne($: EngineInterface, id: string, version: string, folder: string): Promise<Check> {
  try {
    // The folder goes in as one argument, so no shell reads it.
    const run = await $.process.run(['claude', 'plugin', 'validate', folder], { timeoutMs: 60000 })
    const text = run.stdout + run.stderr

    return { id, version, ...parseValidate(text), ...declared(text) }
  } catch (error) {
    const problem = error instanceof Error ? error.message : String(error)
    return { id, version, verdict: 'unknown', warnings: 0, errors: 0, problem, hooks: [], calls: [] }
  }
}

Then parseValidate reads the verdict from the words Validation failed or Validation passed. It reads the warning and error counts from the lines that say Found N warnings or Found N errors. A separate function, declared, reads the hooks: and calls: lines.

/** Reads the verdict, the counts and the first error of one `claude plugin validate` run. */
function parseValidate(text: string): Pick<Check, 'verdict' | 'warnings' | 'errors' | 'problem'> {
  // Match the words after the status symbol, not the symbol itself.
  const verdict = /^[^\w\n]*Validation failed\s*$/m.test(text)
    ? 'failed'
    : /^[^\w\n]*Validation passed/m.test(text)
      ? 'passed'
      : 'unknown'
  const warnings = Number(text.match(/^[^\w\n]*Found (\d+) warnings?:/m)?.[1] ?? 0)
  const errors = Number(text.match(/^[^\w\n]*Found (\d+) errors?:/m)?.[1] ?? 0)
  // The directory's own findings are left out: they do not change the verdict.
  const problem =
    text.match(/^[^\w\n]*Found \d+ errors?:[\s\S]*?^\s*❯ (.+)$/m)?.[1] ??
    (verdict === 'unknown' ? 'no verdict from the validator' : '')

  return { verdict, warnings, errors, problem }
}
Not confirmed.

These are regular expressions over the validator's printed text. They assume the wording the validator uses today. I did not run the validator on this mod, so that wording is unchecked. A live run would confirm it.

3. The flags

Three checks raise flags, in plain words:

  • A check whose verdict is not passed gets a red line, did not pass validation, with the problem after it. That includes a check with no verdict.
  • Two or more enabled plugins with a tool.call hook get a yellow note. The event name is the text before any {, so a matcher does not hide it.
  • One name enabled under two or more marketplaces gets a yellow note.
  for (const check of checks) {
    if (check.verdict !== 'passed') {
      const reason = check.problem ? `: ${check.problem}` : ''
      flags.push({ text: `${check.id} did not pass validation${reason}`, severity: 'fail' })
    }
  }

  const hookers = checks
    .filter(check => check.hooks.some(hook => hook.split('{')[0] === 'tool.call'))
    .map(check => check.id)
  if (hookers.length >= 2) {
    flags.push({
      text: `${hookers.length} enabled plugins hook tool.call, and their order matters: ${hookers.join(', ')}`,
      severity: 'note',
    })
  }
Why the order matters.

The note says the order of tool.call hooks matters. The engine's types say the chain's tiers nest, outermost first, and that same-event hooks "nest in this order and no other way". That supports the note. I checked it against those type comments only. I did not run two hooks to see the effect.

4. The pane and the Refresh button

The command.run hook for mod-doctor opens the pane with the id mod-doctor, starts the audit, and returns the text Mod doctor opened. It does not wait for the audit. The ui.render hook for the Pane component draws the pane from a state atom. That atom holds a status (idle, reading, ready or failed), any error, and the audit result. The audit writes the state with update. The Refresh button calls the audit again. While a run is reading, the button says Auditing…, and the audit returns at once. That is the one-run guard:

/** Lists the plugins, validates each enabled one with a folder, and stores the findings. One run at a time. */
async function audit($: EngineInterface): Promise<void> {
  const current = await read($, view)
  if (current.status === 'reading') {
    return
  }
  await update($, view, v => ({ ...v, status: 'reading', error: '' }))
The guard is not atomic.

The guard reads the state, checks it, and then writes reading. Those are separate awaits. Two presses that both read idle before either write could both start a run. The engine's update retries when the version has changed, but that protects the write, not the check before it. The likely effect is two runs, each writing a full result. The source does not fix this, and I did not change it.

How to use it

Install it from the marketplace.

claude plugin marketplace add coherentsolutionstrainingcenter/claude-code-mods
claude plugin install mod-doctor@waraxe-claude-mods
  • Type /mod-doctor. The handler ignores any arguments. The pane opens and the audit starts.
  • Read the summary line: installed, enabled, validated, and the time of the check. Then read the flags. Red lines are failures. Yellow lines are notes.
  • Read each validated plugin. Its line has a tick for a pass, a cross for a fail, or a question mark for no verdict, then its id, version and verdict. Under it are its hooks and its calls.
  • Read the footer. It lists enabled plugins with no folder, and disabled plugins. A disabled plugin appears in the disabled line even when it has no folder.
  • Press Refresh to run the audit again.

What it costs. The mod's own code makes no model calls. An audit runs claude plugin list once, then claude plugin validate once for each enabled plugin with a folder. On the machine I checked, 14 enabled plugins had a folder, so one audit made 15 runs. Each run has a 60-second limit.

Where the README and the source differ.
  • The README says the pane shows each plugin's warnings and errors. The source shows the error count only on a failed check, and the warning count only on a passed one.
  • The README says a plugin that fails validation is flagged. The source also flags a check with no verdict, with the same red line.
  • The README says an audit takes a few seconds per enabled mod. The source sets a 60-second limit per run and does not measure time, so I could not confirm the figure.
  • The README says the audit runs only read-only commands. The source runs two claude plugin commands and does not show what they do, so I could not confirm that.

Limits.

  • The validator checks structure and the calls a module declares. It does not check behaviour. A pass does not show that a mod works, and the pane's last line says so.
  • The verdict depends on the validator's wording. If that wording changes, the parsing can miss it.
  • I did not install mod-doctor, enable it, or open its pane. The mod has not been tested in a live session.

Check yourself

Why does mod-doctor read the text of claude plugin list instead of its JSON?

The source treats only a Read from line as the folder, and it does not explain the choice. On the machine I checked, the JSON installPath pointed into the plugin cache, while the text form named the source folder.

A validator run throws an error. What does the pane show, and does it raise a flag?

The check gets the verdict unknown. The pane shows a question mark and the words "no verdict". The flags also add a red line, "did not pass validation", with the error text after it.

A plugin shows a tick and no flags. Does that mean the mod works?

No. The validator checks the manifest structure and the calls the module declares. It does not run the mod or test what it does.
