What it is

Aside adds /aside, which opens a pane beside the transcript. You ask a question about the session so far, and a tool-less fork of the session's own transcript answers it. The side chat cannot call tools, edit files or submit prompts, and nothing from it goes back into the main thread.

This matters for your mission because it is the clearest example in this set of a mod that is read-only by design. Its validator output lists every hook and call it makes, so you can check that claim yourself.

How it was built

The module is one file, hooks/register.ts, of about 260 lines. It uses no JSX. The pane is drawn with Box, Text, Input and Button calls. The module is also small in what it touches. The README copies the list that claude plugin validate --strict prints for it: $.clock.now, $.command.register, $.model.complete, $.model.fork, $.session.messages, $.ui.close, $.ui.invalidate, $.ui.open and $.ui.resolve. There is no $.fs, $.process, $.http, $.store, $.tool or $.prompt.

1. Keep a small host object, and register the command

session.start builds a host object. It wraps each engine call that the module needs, so the rest of the file only calls host.fork, host.complete and so on. The /aside command is registered with immediate: true. The engine's type notes say this flag lets a command run mid-turn.

  on('session.start', async ($, e, next) => {
    host = {
      fork: prompt => $.model.fork({ prompt }),
      messages: () => $.session.messages(),
      complete: prompt => $.model.complete({ model: liveModel, maxTokens: 400, system: LIVE_SYSTEM, prompt }),
      invalidate: () => $.ui.invalidate('ui.render'),
      open: () => $.ui.open({ id: PANE_ID, title: 'aside', focus: true }),
      close: () => $.ui.close({ id: PANE_ID }),
      now: () => $.clock.now(),
    }
    await $.command.register({
      name: 'aside',
      description: 'Read-only side chat about this session (opens a pane; Tab focuses its input)',
      argumentHint: '[question]',
      immediate: true,
    })
    return next(e)
  })

2. Ask a fork of the transcript

run sends the question to $.model.fork. A fork replays the session's own transcript, so the prompt cache is shared with the main thread. The answer is stored with its usage: how many tokens were read from the cache, how many were new, and how many came out. If there is no snapshot yet, run falls back to the live path in step 3.

  function run(h: Host, entry: Exchange): void {
    inFlight += 1
    void h
      .fork(promptOf(entry.q))
      .then(async r => {
        if (r !== null) {
          entry.a = clip(r.text)
          entry.kind = 'fork'
          entry.note = `read ${r.usage.cache_read_input_tokens} · new ${r.usage.input_tokens + r.usage.cache_creation_input_tokens} · out ${r.usage.output_tokens}`
          return
        }
        if (liveFallback) {
          await answerLive(h, entry)
          return
        }
        entry.queued = true
        queued.push(entry)
      })
      .catch((err: unknown) => {
        entry.a = `(no answer: ${err instanceof Error ? err.message : String(err)})`
      })
      .then(() => {
        if (entry.a !== null) entry.ms = h.now() - entry.askedAt
        inFlight -= 1
        h.invalidate()
      })
  }

3. Answer from the transcript text when no turn has finished

A fork needs a completed turn to fork from. Until the first turn ends there is no snapshot. The code expects $.model.fork to return null then, and when that happens with liveFallback on, answerLive sends the transcript text through $.model.complete instead. That call is not cached, and the transcript is cut to its last 60,000 characters. The answer is marked live in the pane.

Check this on a newer engine. The return value has changed.

The README says the mod was tested on 2.1.270. The engine types in this workspace (build 2.1.308) say $.model.fork never returns null. It returns { isAnswered: false, reason: 'nothing-to-fork' } instead. Read against those types, the r !== null check in run is always true. Then r.text is undefined, clip throws on it, and the question shows "(no answer: …)" instead of falling back to the live path. This is a reading of the code and the types, not a test run, so confirm it in a session before you rely on the first-turn fallback.

  async function answerLive(h: Host, entry: Exchange): Promise<void> {
    const messages = await h.messages()
    if (messages.length === 0) {
      entry.a = '(nothing to ask about yet: the transcript is empty)'
      return
    }
    let rendered = messages.map(m => `${m.role.toUpperCase()}: ${m.text}`).join('\n\n')
    if (rendered.length > LIVE_TRANSCRIPT_CHARS) rendered = `…${rendered.slice(-LIVE_TRANSCRIPT_CHARS)}`
    const text = await h.complete(`Transcript so far:\n\n${rendered}\n\n${promptOf(entry.q)}`)
    entry.a = clip(text)
    entry.kind = 'live'
    entry.note = `${rendered.length} chars of transcript sent uncached`
  }

4. Put the side chat's own history into each prompt

A fork takes exactly one user message. So promptOf writes the last few side exchanges into the prompt, as Q: and A: pairs, and then adds the new question. The number of pairs comes from the maxHistory option, which defaults to 8.

  const promptOf = (question: string): string => {
    const prior = history
      .filter(x => x.a !== null && x.kind !== undefined)
      .slice(-maxHistory)
      .map(x => `Q: ${x.q}\nA: ${x.a}`)
      .join('\n\n')
    return [
      'This is a read-only side question about the conversation above. Answer from the transcript so far.',
      'Do not use tools, do not propose edits, do not continue the main task; answer briefly in plain prose.',
      prior === '' ? '' : `Earlier side questions and their answers:\n\n${prior}`,
      `Side question: ${question}`,
    ]
      .filter(part => part !== '')
      .join('\n\n')
  }

5. Draw each exchange with function calls

The ui.render hook draws one block for each question. The block shows the question, then "thinking…" or "waiting for this turn to end…", then the answer. The footer shows where the answer came from and how long it took. This excerpt is the part that draws a row.

    const rows = shown.map((x, i) =>
      Box({
        key: `x${i}`,
        flexDirection: 'column',
        marginTop: i === 0 ? 0 : 1,
        width,
        children: [
          Text({ bold: true, color: 'cyan', wrap: 'wrap', children: `you: ${x.q}` }),
          x.a === null
            ? Text({ dimColor: true, children: x.queued ? 'aside: waiting for this turn to end…' : 'aside: thinking…' })
            : Text({ wrap: 'wrap', children: `aside: ${x.a}` }),
          x.a !== null && x.ms !== undefined
            ? Text({ dimColor: true, children: `${x.kind ?? 'error'} · ${x.ms} ms${x.note ? ` · ${x.note}` : ''}` })
            : null,
        ],
      }),
    )

6. Take the input and the presses in hooks, not in closures

The pane's input and buttons send their events to hooks. A closure in a drawing lives only for that drawing. If a submit arrives while the pane is being redrawn, the closure can be lost. The hook still gets the event and its value. So the question goes to ask from the ui.input hook, and Clear and Close are handled in ui.press.

  // The pane's events are answered here rather than in the element closures:
  // a closure handle belongs to one drawing, and a submit that lands during a
  // redraw is dropped by core ("no handler is held under handle N"), while the
  // hook still sees the event and its value.
  on('ui.input', { plugin: 'aside', element: 'q' }, ($, e, next) => {
    if (e.kind !== 'submit') return next(e)
    ask(e.value)
    return { element: e.element, value: e.value }
  })

  on('ui.press', { plugin: 'aside' }, ($, e, next) => {
    if (e.element === 'clear') {
      history = []
      host?.invalidate()
      return { element: e.element }
    }
    if (e.element === 'close') {
      void host?.close()
      return { element: e.element }
    }
    return next(e)
  })
Function hooks are early access.

The README says the module needs Claude Code 2.1.270 or newer, with CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 set. Without that variable the module is not loaded and /aside does not exist. The README also says the API changes between releases, and the module was tested only against 2.1.270.

How to use it

claude plugin marketplace add JayDoubleu/aside
claude plugin install aside@aside

The marketplace is named aside. Set CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 in the environment before you start Claude Code. The README also shows a checkout install, CLAUDE_CODE_ENABLE_FUNCTION_HOOKS=1 claude --plugin-dir ./aside.

  • Type /aside to open the pane. Type /aside what has changed so far? to open it and ask at once.
  • Press Tab to move into the pane's input. Type a question and press Enter.
  • Press Esc to give the keys back to the composer. Press ctrl+x then tab to focus the pane again, and ctrl+x then x to close it.
  • Read the footer under each answer. For example, fork · 1244 ms · read 72848 · new 242 · out 100 says it was a fork, how long it took and what it cost.
  • Press Clear to empty the side chat. Press Close to close the pane.

Cost. A fork costs one prompt-cache read of the whole session prefix, plus a few new tokens. The README measured 72,848 cache-read tokens on a 73k-token session, about $0.008 on Haiku, and more on the session's own model. Right after /compact, the summary goes in uncached, at about 3k tokens. A live answer sends the transcript text to liveModel as new input.

Limits.

  • A question answers from the last completed turn. If you ask while a turn is running, the answer does not include that turn.
  • Each answer is cut to 1,200 characters. Only the last maxHistory side exchanges (8 by default) are sent with a new question.
  • The mod cannot read files or run commands. It answers from the transcript only, so it cannot check the working tree.
  • The pane docks beside the transcript at 110 columns or wider. A narrower terminal opens it inline above the prompt.

Check yourself

How can you check, without trusting the README, that the mod cannot read files or reach the network?

Run claude plugin validate . --strict in the plugin folder. It prints the hooks and calls the module makes, and the README's copy of that list has no fs, process, http, store, tool or prompt verbs. You can also search hooks/register.ts for $.fs, $.process or $.http. The search finds nothing.

Why does the /aside command return {}, and not a text message?

A { text } answer would become a message in the main transcript, and the model would read it. Returning {} opens the pane and asks the question, but leaves the main thread with nothing new. The pane shows the answer instead.
