What it is

ctx-handoff is a toolkit for long sessions. This lesson follows its handoff. With auto_handoff on, at 600,000 tokens it waits for Claude and its subagents to finish, has a fork write a summary, clears the chat, and sends the summary as the first message of the fresh conversation. auto_handoff is off by default, so Claude Code's own compact takes over unless you turn it on or run /handoff now.

The same plugin keeps the prompt cache warm while you are away, keeps project notes, and nudges Claude when it repeats a failure or says it is done without checking. The guide covers those parts.

It matters for your mission because it clears your chat and submits a prompt for you, and you must be able to point to the hooks and calls that do that before you tell others to install it.

How it was built

The hooks live in hooks/register.ts, with settings in hooks/config.ts and the texts in hooks/i18n.ts. The code comments are in Traditional Chinese; the prose below says what they mean. The steps follow one automatic handoff, then the cache keeping that runs while you are away.

1. Declare the hook module

hooks/hooks.json names one module. The engine loads it and calls the register function it exports.

{ "modules": ["./register.ts"] }

2. Set the threshold

Each setting has a type, a range and a default. auto_handoff is off, and the threshold is 600,000 tokens. On a smaller context window, thresholdOf takes the window times window_ratio (0.8) when that is lower.

export const SETTINGS: readonly SettingSpec[] = [
  { key: 'auto_handoff', kind: 'bool', d: false },
  { key: 'threshold', kind: 'num', min: 50_000, max: 2_000_000, step: 50_000, d: 600_000 },
  { key: 'window_ratio', kind: 'num', min: 0.3, max: 0.95, step: 0.05, d: 0.8 },
export const thresholdOf = (window: number) => Math.min(cfg.threshold, Math.floor(window * cfg.windowRatio))

3. Decide at each stop

The classic.Stop hook calls onStop each time the main conversation stops. With auto_handoff off, or under the threshold, it returns. If background tasks, one-shot schedules or subagents are still running, it waits, up to a cap: 90% of the window, or 150,000 tokens past the threshold, whichever is lower.

  if (!cfg.autoHandoff) {
    rt.deferral = undefined
    rt.deferToasted = false
    return
  }
  const { context } = await $.session.usage()
  const tokens = context.tokens
  const threshold = thresholdOf(context.window)
  if (tokens === undefined || tokens < threshold) {
    rt.deferral = undefined
    rt.deferToasted = false
    return
  }
  const agents = (await $.agent.list()).filter(a => a.status === 'running').length
  const parts = [tasks && t().stop.tasks(tasks), oneShot && t().stop.oneShot(oneShot), agents && t().stop.agents(agents)].filter(Boolean)
  const partsText = parts.join(t().list)
  let note: string | undefined
  if (parts.length > 0) {
    const cap = Math.min(Math.floor(context.window * DEFER_CAP_RATIO), threshold + DEFER_CAP_EXTRA)
    if (tokens < cap) {
      rt.deferral = t().stop.deferral(partsText, cap)
      $.ui.status(t().status.deferred(partsText))
      $.ui.log(t().stop.deferLog(tokens, partsText))
      if (!rt.deferToasted) { rt.deferToasted = true; $.ui.toast(t().status.deferred(partsText)) }
      return
    }
    note = t().stop.note(partsText, cap)
    $.ui.log(t().stop.capLog(tokens, cap, partsText))
  }

Then it marks the session busy and starts the handoff on a timer, so the hook itself returns at once.

  rt.deferral = undefined
  rt.deferToasted = false
  $.ui.status(undefined)
  beginPresent()
  $.clock.after(0, () => void present($, tokens, 'present', note))

4. Ask a fork for the summary

makeHandoff sends HANDOFF_PROMPT through $.model.fork. The engine types say a fork is one tool-less completion over the session's own transcript, so the API can serve that prefix from its cache. forkWithin stops waiting after HANDOFF_TIMEOUT_MS, 5 minutes. A failure is logged, shown as a toast and stored for /handoff. A good summary is kept in the store, the last five per project.

async function makeHandoff($: EngineInterface, kind: Kind, tokens: number | null, source?: HandoffSource) {
  const sid = source?.sid ?? await $.session.id()
  const started = await $.clock.now()
  const task = { sid, phase: 'generating', at: started } satisfies NonNullable<typeof rt.handoffTask>
  rt.handoffTask = task
  await refreshPanel($)
  try {
  const r = await forkWithin($, HANDOFF_PROMPT, HANDOFF_TIMEOUT_MS, sid)
  if (source && !(await sourceIsFresh($, source))) {
    $.ui.log(t().idle.outdated)
    await stat($, 'away.stale')
    return undefined
  }
  if (!r.isAnswered) {
    $.ui.log(t().handoff.failedLog(forkFailure(r.reason)))
    $.ui.toast(t().handoff.failedToast)
    await recordFailure($, kind, tokens, t().handoff.failGenerate(forkFailure(r.reason)))
    return undefined
  }

HANDOFF_PROMPT, in hooks/handoff.ts, is written in Chinese. The guide describes it: the summary keeps verified work apart from work only changed or only discussed, lists approaches that failed, keeps your limits in your own words, and ends with one next step. It has no word cap.

5. Tell the fresh chat what happened

present puts a short intro, tagged [ctx-handoff], before the summary. Messages you typed during the handoff were held in rt.held. They go in after the summary, and the intro changes to say so.

    const why = kind === 'manual' ? t().handoff.whyManual : t().handoff.whyTokens(tokens ?? 0)
    const included = [...rt.held]
    delivered = included.length
    const intro = `${tag} ${included.length === 0 ? t().handoff.intro(why) : t().handoff.introHeld(why)}`
    const text = `${intro}${note ? t().handoff.note(note) : ''}\n\n${handoff}${included.length ? `\n\n${heldBlock(included)}` : ''}`
    const failed = await clearAndSubmit($, text)

The English intro, from hooks/i18n.ts, asks the new chat to state what it understood and wait.

    intro: why =>
      `The previous conversation was cleared automatically because ${why}. Here is the handoff: read it, tell me in a few lines the current state and next step as you understand them, then wait for the user's instructions. Do not start working yet.`,
    introHeld: why =>
      `The previous conversation was cleared automatically because ${why}. Here is the handoff and the messages the user sent during the handoff: respond to the user's last message below, using the handoff as context.`,

6. Clear, then submit

clearAndSubmit first saves the text under a pending key. It then runs /clear with $.command.run and sends the text with $.prompt.submit. The comment says the session is marked as handed off first, so the new chat's first message does not also get the progress note, and the mark is undone if /clear fails. If /clear fails, you are still in the old chat, so the pending text is deleted. If only the submit fails, the text stays for /handoff resend.

  const key = pendingKey(sid)
  await $.store.set(key, { text, project: await projectKey($) } satisfies PendingSubmit)
  await touchSeen($, key)
  rt.myPending = { sid }
  rt.pendingToasted = false
  // 新對話第一則訊息（就是這份 handoff）開頭不要再提供同一段的進度備忘：先標記，/clear 失敗再還原
  await markHanded($, sid, true)
  try {
    await $.command.run({ command: 'clear' })
  } catch (err) {
    await $.store.delete(key)
    rt.myPending = undefined
    await markHanded($, sid, false)
    return { stage: 'clear', reason: String(err) }
  }
  try {
    await submitText($, text)
  } catch (err) {
    return { stage: 'submit', reason: String(err) }
  }
  await $.store.delete(key)
  rt.myPending = undefined
  return undefined

7. Keep the cache warm while you are away

After each turn, schedule sets a timer for idle_minutes (50). When it fires, onIdle sends a fork whose prompt means "Reply only OK". The comment says this is the cheapest fork: it reads the cache once. The first refresh also updates the project notes. After max_refresh (3) refreshes, onIdle writes an away handoff instead and does not clear. Your next message then asks you to choose /handoff resume or /handoff continue.

  if ((await isRefreshOn($)) && rt.refreshes < cfg.maxRefresh) {
    const task = { sid, phase: 'refresh', at: await $.clock.now() } satisfies NonNullable<typeof rt.handoffTask>
    rt.handoffTask = task
    await refreshPanel($)
    try {
    // 刷新用最便宜的 fork（只回 OK）讀一次快取；整理是另一個不帶歷史的請求，有新對話才跑
    const r = await forkWithin($, '只回覆 OK', HANDOFF_TIMEOUT_MS, sid)
    if (!(await sourceIsFresh($, { sid, activity }, true))) return
    if (!r.isAnswered && r.reason === 'nothing-to-fork') {
      $.ui.log(t().idle.refreshSkipped)
      return
    }
    if (rt.refreshes === 0 && await isDistillOn($)) await distill($, t().distill.why.idle)
    if (!(await sourceIsFresh($, { sid, activity }, true))) return
    rt.refreshes += 1
    $.ui.log(r.isAnswered
      ? t().idle.refresh(rt.refreshes, cfg.maxRefresh, r.usage.cache_read_input_tokens, r.usage.cache_creation_input_tokens)
      : t().idle.refreshFailed(rt.refreshes, cfg.maxRefresh, r.reason))
    await schedule($)
    return
Two things to check before you rely on it.
  • The README says: on an API key, Bedrock or Vertex the cache lasts only 5 minutes, so run /handoff refresh off. The guide says this is not detected for you.
  • The README calls ctx-handoff experimental, because Claude Code mods are still in early access.

How to use it

claude plugin marketplace add <org>/waraxe-claude-mods
claude plugin install ctx-handoff@waraxe-claude-mods

Replace <org> with the GitHub account that hosts this marketplace. The README asks for Claude Code 2.1.287 or later, and says it was tested up to 2.1.302.

  • Start a new session and type /handoff. It shows context use, what is on, the latest progress note and recent errors. The README's example starts with context 12034 / threshold 600000 (window 1000000).
  • To hand off at the threshold, open /handoff panel, press 5 for Settings, and turn on auto_handoff.
  • /handoff now hands off at once and clears. /handoff dry shows a summary and its cost without clearing.
  • After being away: /handoff resume starts fresh from the summary, and /handoff continue stays where you were.
  • If the new chat did not get the summary: /handoff resend, or /handoff resend <source-session-id> after a restart.
  • Other commands: /handoff distill updates project notes now, /handoff away pause|resume, /handoff refresh on|off, /handoff distill on|off, and /handoff guard. If /handoff is taken by your own command or skill, the command is /ctx-handoff.

Settings. All of them are on the panel's Settings tab, not in /config. The main ones: auto_handoff (off), threshold (600000), window_ratio (0.8), idle_minutes (50, from 5 to 59), max_refresh (3), distill_every (30), min_tokens (30000) and notes_model (Sonnet 5.5 or Opus 5.5). You can also set them in ~/.claude/settings.json under pluginConfigs. The code reads the first key that starts with ctx-handoff@, so from this marketplace the key is ctx-handoff@waraxe-claude-mods. A value set on the panel wins over the file.

Cost. From the guide:

  • A handoff is one request that reads the conversation, mostly from cache, and writes the summary. The guide says about 30 seconds at 800,000 tokens. A comment in config.ts says 45 to 120 seconds since the word cap was removed.
  • A cache refresh reads the conversation from cache, at about a tenth of the normal input price, at most 3 times per idle period.
  • A notes update sends only the new part of the conversation to Sonnet 5.5 at low effort. A short one takes about 1,200 tokens.
  • The nudges make no requests. It makes no network requests of its own and starts no programs.

Limits. From the guide:

  • On a 5-minute cache, turn cache keeping off with /handoff refresh off.
  • Notes follow the folder you start in, and are not shared across projects.
  • The progress note is only as fresh as the last notes update. Run /handoff distill before /clear if you want it exact.
  • Attachments typed during a handoff cannot be held. You are asked to paste them again.
  • Other open sessions pick up a settings change on their next message.
  • Updating the mod in the middle of a handoff may lose a held message.

Check yourself

auto_handoff is off. What does ctx-handoff do when the chat reaches 600,000 tokens?

No handoff. onStop returns as soon as it sees !cfg.autoHandoff, so Claude Code's own compact takes over. Cache keeping and notes still run, and /handoff now still works.

Why does clearAndSubmit save the text under a pending key before it runs /clear?

Once /clear has run, the old chat is gone. If the submit then fails, the saved text is the only copy, and /handoff resend sends it from the store. The key is deleted only after a good submit, or when /clear itself fails and you are still in the old chat.
