What it is

The README says the plugin was made for the savvy-flow skill and is useful with any subagents. The bar shows the flow's title, its phase, accepted tasks out of planned ones, and a button with the crew size that opens the panel. The panel lists every subagent of the session, with model, effort, task progress, context, estimated cost and time. The savvy-flow skill itself is not in this marketplace.

It serves your mission because it uses seven hook events, two tools of its own and a prompt change, and each one has a reason you can name.

How it was built

Everything is in one module, hooks/register.tsx. hooks/hooks.json names it with { "modules": ["./register.tsx"] }. The steps follow one flow, from the tools to the drawn bar.

1. Keep the flow, the runs and the panel in atoms

An atom is a named value with a starting value. flow is the plan the main session reports. agents is one record per subagent run. panel holds the panel's toggles. now is the clock the drawings read. types/index.d.ts gives each key its type.

const flow = atom({ plugin: 'savvy-progress', key: 'flow' } as const, null)
const agents = atom({ plugin: 'savvy-progress', key: 'agents' } as const, [])
const panel = atom({ plugin: 'savvy-progress', key: 'panel' } as const, {
  isCompact: false,
  isDoneCollapsed: false,
  autoOpenedFor: '',
})
const now = atom({ plugin: 'savvy-progress', key: 'now' } as const, 0)

2. Register the two tools and the command

On session.start the module registers a progress tool, the step tool below, and the /agents-info command. The types say a registered tool is called as mcp__<plugin>__<name>, so these become mcp__savvy-progress__progress and mcp__savvy-progress__step. The comment says isDeferred: false keeps the step tool in every agent's tool list, not behind ToolSearch. The hook also starts a one-second clock that moves now only while a run is going.

    await $.tool.register({
      name: 'step',
      description:
        'For savvy-flow workers: report progress on your own task to the agents panel. ' +
        'Right after reading the brief, call it with `total` (your plan in 3-8 steps) and `done: 0`; ' +
        'call it again as each step finishes. Cheap and silent: it only draws a bar.',
      inputSchema: {
        type: 'object',
        properties: {
          done: { type: 'integer', minimum: 0, description: 'Steps finished so far.' },
          total: { type: 'integer', minimum: 1, description: 'Steps planned; may change if the plan changes.' },
          note: { type: 'string', description: 'The step in progress, a few words.' },
        },
        required: ['done'],
      },
      // In every agent's tool list, not behind ToolSearch: workers do not go looking for it.
      isDeferred: false,
    })
    await $.command.register({
      name: 'agents-info',
      description: 'Show or hide the panel of subagents: running, finished and planned, with model, context, cost and time',
    })

3. Take flow reports from the main session only

This tool.call hook answers the progress tool itself and never calls next(e). The types say a registered tool needs a hook that returns its result. A call with an agentId comes from a subagent, so it is ignored. A new title starts a new flow: finished runs are cleared, running ones stay. merge then folds in the report. Fields left out keep their old values. A report with tasks opens the panel, once per flow title.

  on('tool.call', { tool: TOOL }, async ($, e) => {
    // The flow is the main session's: a call from a worker's loop carries its agentId
    // and changes nothing, or any subagent could rename, finish or reset the flow.
    if (e.agentId) return { result: 'ignored: only the main session reports the flow' }
    const input = e as unknown as ProgressInput
    const prev = await read($, flow)
    if (isNewFlow(prev, input) && input.title !== undefined) {
      // A new flow starts with a clean list; agents still running stay.
      await update($, agents, list => list.filter(a => a.status === 'running'))
    }
    const next = await update($, flow, p => merge(p, input))
    if (next && input.tasks?.length) await autoOpen($, next.title)
    return { result: `ok: ${label(next ?? blank())}` }
  })

4. Brief each savvy worker and add a row for every subagent

agent.spawn runs before a subagent starts. For a savvy-* worker whose prompt does not name the step tool, it adds STEP_BRIEF to the end of the prompt before next. The comment says workers skip the step tool when the system prompt asks, but follow the same request in the brief. If the start is denied, the hook stops there. Otherwise it adds a run record, and counts rounds by matching descriptions. Only the last 200 runs are kept.

  on('agent.spawn', async ($, e, next) => {
    const isUnbriefed = e.subagentType.startsWith('savvy-') && !e.prompt.includes(STEP_TOOL)
    const started = await next(isUnbriefed ? { ...e, prompt: e.prompt + STEP_BRIEF } : e)
    if (started.deny !== undefined) return started

    const at = await $.clock.now()
    await update($, agents, list => {
      const round = 1 + list.filter(a => norm(a.description) === norm(e.description) && e.description).length
      const run: AgentRun = {
        id: started.agentId ?? e.tool_use_id,
        agentId: started.agentId,
        type: e.subagentType,
        description: e.description,
        model: started.model,
        status: 'running',
        startedAt: at,
        contextTokens: 0,
        contextMax: windowOf(started.model),
        tokens: 0,
        costUsd: 0,
        steps: 0,
        round,
      }
      return [...list.filter(a => a.id !== run.id), run].slice(-200)
    })

5. Count each model request of a subagent

turn.step fires for each model request. It streams, so the hook is a generator, and yield* next(e) gives the whole response. The hook only acts on a subagent's request (agentId) that has usage. Context is the token count of the last request. Tokens and cost add up across requests. Later, turn.complete marks the run done when the reason is answer, and failed otherwise.

  // Each model request of a subagent: live context, tokens and cost.
  on('turn.step', async function* ($, e, next) {
    const result = yield* next(e)
    const agentId = e.agentId
    const usage = result.usage
    if (!agentId || !usage) return result

    const model = usage.model || e.model
    await update($, agents, list =>
      list.map((a): AgentRun =>
        a.agentId !== agentId
          ? a
          : {
              ...a,
              model,
              effort: typeof e.effort === 'string' ? e.effort : a.effort,
              status: 'running',
              endedAt: undefined,
              contextTokens:
                (usage.input_tokens || 0) +
                (usage.cache_read_input_tokens || 0) +
                (usage.cache_creation_input_tokens || 0) +
                (usage.output_tokens || 0),
              contextMax: windowOf(model),
              tokens:
                a.tokens +
                (usage.input_tokens || 0) +
                (usage.output_tokens || 0) +
                (usage.cache_read_input_tokens || 0) +
                (usage.cache_creation_input_tokens || 0),
              costUsd: a.costUsd + costOf(model, usage, true),

6. Estimate the cost from a price table

The comment says the engine reports tokens, not money, so the cost is an estimate. PRICES gives dollars per million tokens for input, output, cache reads and cache writes. The first pattern that matches the model id wins. A Haiku 5.5 request with a prompt over 100,000 tokens uses the long-prompt prices. An unknown model gets [4, 20, 0.2, 8].

const priceOf = (model: string, prompt: number): Price => {
  const id = model.toLowerCase()
  if (prompt > HAIKU_LONG_PROMPT && /haiku-5-5/.test(id)) return HAIKU_LONG
  return PRICES.find(([re]) => re.test(id))?.[1] ?? [4, 20, 0.2, 8]
}

// `isRequest` says the usage is one model request, which is what a prompt-length price
// is set by; a turn's sum is priced at the model's ordinary prices.
const costOf = (model: string, u: Usage, isRequest: boolean): number => {
  const prompt = isRequest ? (u.input_tokens || 0) + (u.cache_read_input_tokens || 0) + (u.cache_creation_input_tokens || 0) : 0
  const [i, o, r, w] = priceOf(model, prompt)
  return (
    ((u.input_tokens || 0) * i +
      (u.output_tokens || 0) * o +
      (u.cache_read_input_tokens || 0) * r +
      (u.cache_creation_input_tokens || 0) * w) /
    1e6
  )
}

7. Draw the bar above the prompt

The AbovePrompt hook passes when there is no flow or a survey is open. Otherwise it draws its own row with the other mods' bands beneath it. The comment says Claude Code's own placeholder is never nested, because the desktop drops a band that nests it. The ×N button opens or closes the panel. The ✕ button clears the flow. On the desktop the row is one SVG. In the terminal it is Text, with a bar of █ and ░.

  on('ui.render', { component: 'AbovePrompt' }, async ($, e, next) => {
    const f = await read($, flow)
    if (f === null || e.props.hasSurvey) return next(e)
    // Draw this row with the other mods' bands beneath it. Claude Code's own placeholder ({ type: 'engine' }) is
    // never nested: the desktop drops a band that nests it.
    const drawn = await Promise.resolve(next(e)).catch(() => null)
    const below = drawn && typeof drawn === 'object' && (drawn as { type?: string }).type !== 'engine' ? drawn : null

    const ui = $.ui.resolve(e)
    const { Box, Text, Button } = ui
    const list = await read($, agents)
    const crew = list.length + plannedOf(f, list).length
    const isWorking = list.some(a => a.status === 'running')
    const crewButton = (
      <Button key="savvy-agents" label={`×${crew}`} plain onPress={() => void togglePane($)} />
    )
    const percent = `${Math.round(ratio(f) * 100)}%`
    const dismiss = (
      <Button
        key="savvy-dismiss"
        label="✕"
        plain
        role="dismiss"
        onPress={() => update($, flow, () => null)}
      />
    )

How to use it

claude plugin marketplace add <org>/waraxe-claude-mods
claude plugin install savvy-progress@waraxe-claude-mods

Replace <org> with the GitHub owner of this marketplace. The marketplace README says to run /reload-plugins or start a new session after the install.

  • /agents-info opens or closes the agents panel. /agents-info open opens it, or brings it forward from behind another tab, without toggling.
  • The bar appears once something reports progress, or a savvy-* worker starts. The README says savvy-flow reports progress.
  • Tools it adds: mcp__savvy-progress__progress for the main session's plan, phase and accepted tasks, and mcp__savvy-progress__step for a worker's own steps (done, total, note). A worker that does not report shows its context fill in grey instead.
  • Setting language: auto (default), en, ru or he. Hebrew draws the bar and the panel right to left. auto follows Claude Code's language setting, then the system locale, and falls back to English.
  • Setting autoOpen: savvy (default) opens the panel when a savvy-* worker starts or a plan is reported. any also opens it, once per session, when any other subagent starts.
  • Set both in /config. For a mod loaded by hand, the README gives this for ~/.claude/settings.json: 
    { "pluginConfigs": { "savvy-progress": { "options": { "language": "ru" } } } }
  • Cost: the plugin makes no model call of its own. The README says the cost it shows is a rough estimate from token counts and a built-in price table (list prices as of 2026-10-10), not a bill.

Limits

  • Cache writes are priced at the 1-hour rate. The README says a session that writes 5-minute entries is overestimated there.
  • Only the main session can report the flow. A worker's progress call is ignored, and a step call from the main session is ignored too.
  • The panel keeps the last 200 runs. A plan keeps at most 200 tasks, and a title at most 120 characters.
  • The context window is guessed from the model name: 200K for Haiku 4 and Claude 3 models, 1M for the rest.
  • The README says prefers-reduced-motion stops the crab animations.

Check yourself

A subagent calls the progress tool with finished: true. What changes?

Nothing. The hook sees e.agentId and returns "ignored: only the main session reports the flow". It never reaches merge. The comment says this stops any subagent from renaming, finishing or resetting the flow.

A savvy-light worker never calls the step tool. What does the bar in its panel row show?

Its context fill, drawn grey. progressOf returns null for a running run with no stepTotal, and the row then falls back to the context percent. A run marked done always shows a full bar.
