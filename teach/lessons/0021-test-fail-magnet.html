What it is

test-fail-magnet watches the Bash tool that Claude uses. When Claude runs a known test command, the mod reads the printed output and keeps up to ten failing lines in a Failing tests pane. Fix sends those lines to Claude as a prompt, and Dismiss clears them.

It matters for your mission because MISSION.md asks you to name each mod's hook events and API calls and say why, and this mod uses one hook, one atom and one pane.

How it was built

The whole mod is one file, hooks/register.tsx, 86 lines long. It has four parts, which the steps below take in order.

1. Recognise a test run by its command

The file starts with a table called RUNNERS. Each row has a run pattern, which is matched against the command text, and a lines pattern, which picks the failing lines from the output. The first row whose run pattern matches the command is used.

// Test runs by command, each with the pattern that finds a failing line in its output.
const RUNNERS: { run: RegExp; lines: RegExp }[] = [
  { run: /\b(npm|pnpm|yarn)\s+(run\s+)?test\b|\bnpx\s+(jest|vitest)\b/, lines: /[✕×]|^FAIL / },
  { run: /\bpytest\b/, lines: /^FAILED / },
  { run: /\bgo\s+test\b/, lines: /--- FAIL:/ },
  { run: /\bcargo\s+test\b/, lines: /^test .* \.\.\. FAILED$/ },
]

Commands with no matching row, such as swift test, are ignored. Their runs leave the list as it is.

Matching is by text, not by meaning. A command that only mentions a test run also counts. For example, grep "npm test" matches the npm row. The mod never checks the exit status.

2. Read the output in a tool.call hook

The hook is registered for tool.call with the matcher { tool: 'Bash' }, so it sees only Bash calls. The first argument, $, is the engine handle. next(e) runs the hooks that come after this one, then the engine's own code, which includes the permission prompt and the tool itself. The result comes back as ran, and ran.text holds the output.

  on('tool.call', { tool: 'Bash' }, async ($, e, next) => {
    const lines = RUNNERS.find(runner => runner.run.test(e.command))?.lines
    // A background run returns before its output exists, so it must not clear the list.
    if (lines === undefined || e.run_in_background === true) {
      return next(e)
    }

    const ran = await next(e)
    if (ran.deny !== undefined) {
      return ran
    }

    const found = failures(ran.text ?? '', lines)
    await update($, failing, () => found)
    if (found.length > 0) {
      void $.ui.open({ id: PANE, title: 'Failing tests' })
    }

    return ran
  })

The hook does not decide whether the command runs. It lets the call go through, then reads what came back. If a hook that runs after this one, or the engine itself, refused the call, ran.deny holds the reason. The hook returns that refusal and leaves the list alone.

Background runs are skipped. A background run returns before its output exists. If the hook cleared the list at that point, the last real result would be lost, so the hook returns early.
The hook never denies a run. It only reads the output. The one refusal it handles is one that another hook or the engine has already given, and it passes that on unchanged.

3. Pick the failing lines in failures()

This helper turns the output into the list the pane shows. It returns a Failing, which types/index.d.ts declares as a plain array of strings. The steps run in this order:

  • split('\n') cuts the output into lines.
  • trim() removes spaces at both ends, so the ^ patterns in RUNNERS can match indented lines.
  • filter keeps the lines that match the runner's lines pattern.
  • new Set drops repeats and keeps the first copy of each line.
  • slice(0, SHOWN) keeps the first ten. slice(0, LINE_MAX) then cuts each one to 160 characters.
/** The matching lines, trimmed and cut, without repeats: at most SHOWN of them. */
function failures(text: string, lines: RegExp): Failing {
  const hits = text
    .split('\n')
    .map(line => line.trim())
    .filter(line => lines.test(line))

  return [...new Set(hits)].slice(0, SHOWN).map(line => line.slice(0, LINE_MAX))
}
Ten is a hard cap. The pane shows the first ten unique matches and gives no count of the rest. A run with twelve failures shows ten, and Fix sends only those ten to Claude.

4. Hold the list in an atom and draw the pane

An atom is a named value that the engine keeps for the plugin. Its key is declared in types/index.d.ts, so the key is typed. The starting value is an empty list. A read returns that starting value until something is written, so it is never undefined.

const failing = atom({ plugin: 'test-fail-magnet', key: 'failing' } as const, [] as Failing)

The pane is drawn by a ui.render hook for the Pane component whose requestId is the pane's id. $.ui.resolve(e) gives the Box, Button and Text constructors. The read call inside the hook subscribes the pane to the atom. A later update therefore makes the engine draw the pane again.

  on('ui.render', { component: 'Pane', requestId: PANE }, async ($, e) => {
    const { Box, Button, Text } = $.ui.resolve(e)
    const list = await read($, failing)

    if (list.length === 0) {
      return (
        <Box>
          <Text dimColor>No failing tests in the last test run.</Text>
        </Box>
      )
    }

    return (
      <Box flexDirection="column">
        {list.map((line, i) => (
          <Text key={`f${i}`} color="red">
            {line}
          </Text>
        ))}

The buttons come last. Fix builds one prompt from the list and sends it with $.prompt.submit. The engine docs say this becomes a turn of its own, started once the session is idle. Dismiss writes an empty list.

        <Box>
          <Button
            key="fix"
            label="Fix"
            onPress={() =>
              void $.prompt.submit({
                text: `Fix the failing tests and run them again:\n${list.map(line => `- ${line}`).join('\n')}`,
              })
            }
          />
          <Button key="dismiss" label="Dismiss" onPress={() => void update($, failing, () => [])} />
        </Box>
      </Box>
    )
  })
Fix does not clear the list. The list stays until the next test run or until you press Dismiss. The mod never closes the pane. After Dismiss, the pane shows the empty message.

How to use it

Install the mod from the marketplace, then ask Claude to run your tests.

claude plugin marketplace add coherentsolutionstrainingcenter/claude-code-mods
claude plugin install test-fail-magnet@waraxe-claude-mods
The catalog does not list this mod yet. /Users/igorwaraxe/Downloads/waraxe-claude-mods/.claude-plugin/marketplace.json has three entries: collision-guard, assumption-check and today-report. Until it has a test-fail-magnet entry, the install line cannot find the mod in that catalog.
  • Ask Claude to run your tests. The command must match one of the four rows in RUNNERS, and Claude's own Bash tool must run it.
  • Read the pane. If the output has a matching line, the pane opens with up to ten lines. If nothing matches, the list is cleared and the pane does not open.
  • Press Fix to send the listed lines to Claude as one prompt, starting with "Fix the failing tests and run them again:".
  • Press Dismiss to empty the list. The pane stays open and shows that there are no failing tests.

Cost

Detection and the pane make no model calls. The hook reads the output in code. Fix submits one normal prompt, which costs tokens like any message you send.

Limits

  • Privacy. Test output can contain secrets. The pane shows only matching lines, cut to 160 characters, and never raw output. A matching line can still carry a secret, such as an assertion message, and Fix sends those lines to the model.
  • Runners. Four rows are read: npm, pnpm and yarn test (also run test), npx jest and npx vitest, pytest, go test, and cargo test. Other runners, such as swift test, rspec, mvn test and gradle test, are not recognised.
  • Your own terminal and background runs. Runs you start in your own terminal are not seen. Background runs are skipped.
  • Width. The engine docs say a pane the person did not ask for is drawn only from 144 columns. This pane opens from a tool call, so the same rule applies. Below that width it waits, undrawn. The README gives the same figure. The mod ignores the result of its open call, so it logs nothing when this happens.
  • A failing hook. The engine docs say a hook that throws is skipped, and the run still goes ahead. The mod has no .catch, so the list may not be updated in that case.
The README and the source disagree in two places. First, the README says the pane opens "when a run fails". The source opens it when the output has at least one matching line. It never reads the exit status or ran.isError, so a run that fails with no matching line clears the list and opens nothing. Second, the README suggests only jest and vitest output is read. The npm, pnpm and yarn row applies the same pattern to any script that npm test runs.

Check yourself

Why does the hook call next(e) before it reads the output?

The output only exists after the Bash call has run. next(e) runs the call and returns its result, and the output is in ran.text. Reading earlier would have nothing to read.

A test run fails to compile and prints no line that the pattern matches. What happens to the list and the pane?

The command still matches a row, so the hook does not return early. failures() returns an empty array, and update writes it, so the list is cleared. The hook makes no open call, because it opens the pane only when found.length is above zero.

How does the pane redraw after Dismiss?

The render hook reads the atom with read($, failing). A read made while a ui.render hook draws subscribes that drawing. When update writes an empty list, the engine draws the pane again, and it shows the empty message.
